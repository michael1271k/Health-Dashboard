# Live Activity — what to do in Xcode

Everything in this document is a **manual Xcode step**. The code is written and
committed; none of it reaches a device until these are done, because Xcode target
membership and Info.plist keys are not things a build script can add here.

Open `ios/App/App.xcworkspace` (the **workspace**, not the project — CocoaPods).

---

## 1. Target membership — the one step that fails silently

`ios/App/Shared/HelixLiveActivity.swift` must belong to **two** targets: **App**
and **HelixWidgetsExtension**.

1. Select `HelixLiveActivity.swift` in the Project navigator. If it is not there,
   drag `ios/App/Shared/HelixLiveActivity.swift` in — **uncheck** "Copy items if
   needed", it is already in the repo.
2. Open the File inspector (⌥⌘1) → **Target Membership**.
3. Tick **App** *and* **HelixWidgetsExtension**. Both.

> **Why this matters more than it looks.** ActivityKit pairs the app's
> `Activity.request` with the extension's `ActivityConfiguration` **by the
> attributes type**. Two identically-named structs compiled into two modules are
> two different types. Get this wrong and the project still builds, the activity
> still starts, and **nothing draws** — no error, anywhere.

`ios/App/App/HelixLiveActivityPlugin.swift` needs **App** only.

`ios/App/HelixWidgets/HelixWorkoutActivity.swift` needs **nothing** — the
`HelixWidgets` folder is a `PBXFileSystemSynchronizedRootGroup`, so every
`.swift` in it is already in the extension. (`ios/App/Shared/` is *not*
synchronized, which is exactly why step 1 exists.)

---

## 2. Deployment target

ActivityKit is iOS **16.1+**. The current settings are fine as they are:

| Target | Deployment target |
|---|---|
| App | 16.6 |
| HelixWidgetsExtension | 16.6 |

Nothing to change. Every ActivityKit symbol is behind `@available(iOS 16.1, *)`
anyway, so a future target *drop* would not break the build either.

---

## 3. Info.plist — already committed, verify it stuck

`ios/App/App/Info.plist` now carries:

```xml
<key>NSSupportsLiveActivities</key>
<true/>
<key>NSSupportsLiveActivitiesFrequentUpdates</key>
<true/>
```

Confirm both are present in Xcode's plist editor. **`NSSupportsLiveActivities` is
the whole entitlement** — ActivityKit needs no paid capability for local updates,
which is the only kind Helix sends. Without the key,
`ActivityAuthorizationInfo().areActivitiesEnabled` is `false` forever and
`Activity.request` throws on a device that fully supports it.

Do **not** hand-edit `ios/App/App/capacitor.config.json` or
`ios/App/App/public/` — those are regenerated by `npx cap sync`.

## 4. Build and sync

```bash
npm run build          # or your usual static export step
npx cap sync ios
```

Then in Xcode: select the **App** scheme, a **real device** (see §6), ⌘R.

## 5. What you should see

Start a workout in the app, then lock the phone or swipe up to the Home Screen.

**Lock Screen / banner**

```

Lateral Raise Cable
Set 3 of 4
LAST TIME  3.75 kg × 16   RPE 10
[12,480 kg] [18 sets] [2 PRs]
```

**Dynamic Island** — compact: the Helix mark on the left, the load to beat on the
right. Long-press to expand: volume, sets, the movement's name, and the LAST TIME
row across the bottom. Tapping anywhere opens `helix://session`, straight back to
the deck.

The card appears when the deck mounts and disappears the moment the session is
committed or discarded — immediately, not under the default four-hour dismissal.

## 6. Known constraints, stated honestly

- **Simulator is not enough.** The Dynamic Island renders in the simulator on an
  iPhone 14 Pro+ profile, but Live Activity behaviour under lock, backgrounding
  and jetsam only tells the truth on hardware. Everything below §1 is unverified
  from this machine by construction.
- **Dynamic Island needs iPhone 14 Pro or newer.** On anything older the Lock
  Screen presentation is the whole feature, and it is the more useful half.
- **Free personal team.** Local Live Activities need no paid capability — unlike
  App Groups, which is why every *other* widget in this project fetches its own
  data over HTTP (see `ios/App/Shared/HelixSnapshot.swift`). If Xcode does object
  at signing time, that is the thing to report back; the code is not the problem.
- **No remote updates.** Pushing a Live Activity over APNs needs a paid program
  and a push entitlement. `pushType: nil` states that decision once, in
  `HelixLiveActivityPlugin.start`.
- **The user can switch these off** per-app in Settings → Helix → Live
  Activities. `liveActivitySupported()` treats that, an old OS, and unsupported
  hardware as one answer — "do not try" — because the caller can do nothing
  different about any of them.

## 7. If nothing draws

In order, because the first is the overwhelming favourite:

1. **Target membership on `HelixLiveActivity.swift`** — §1. Two ticks, not one.
2. `NSSupportsLiveActivities` missing from the **App** target's Info.plist (not
   the extension's — the app is what requests the activity).
3. The plugin never registered: `HelixViewController.capacitorDidLoad()` must
   call `bridge?.registerPluginInstance(HelixLiveActivityPlugin())`. Capacitor 6
   does not auto-discover app-local plugins, and an unregistered plugin rejects
   every call silently.
4. Live Activities switched off for Helix in Settings.
